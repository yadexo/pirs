## 1. Summary

| Severity | Count |

| High | 6 |
| Medium | 12 |
| Low | 11 |

**Do not onboard a real clinic before these are fixed** (details in section 3):

1. **P-1 — any client can check out for free.** A negative quantity in the
   cart cancels out the price of everything else. Reproduced: two treatments
   worth €310 issued for €0.

6. **D-1 — the Next.js version has a critical advisory,** and this app leaves
   the affected image endpoint open to any remote host (I-1).

What is in good shape, so you know where not to spend time: Stripe webhook
handling, refunds, credit and points arithmetic, one-time password links,
upload validation, email HTML escaping, the content security policy, and the
absence of real secrets in the repository or its history.

## 2. Scope and method

**Targets used.** The repository and all 181 commits of history; a local
production build (`npm run serve`) against the local Docker database with
seeded demo accounts; and staging, with GET requests only.

**Not used.** Production was not contacted. No production connection string,
key or token was requested or used.

**How to read the labels.**

- **Verified by running** — I reproduced it against the local build. The
  request or script is given so you can repeat it.
- **Read only** — I found it in the code and did not execute it.

**Local test data.** I created one test platform admin, one test clinic and a
few orders and rate-limit counters in the local database, and removed all of
them afterwards. `git status` is clean apart from this file.

**How actions were called.** Server actions were invoked directly over HTTP,
the way an attacker would, bypassing the user interface: a session cookie
from `POST /api/client-auth/callback/credentials` (or `/api/auth/...` for
staff), then `POST <page>` with a `Next-Action: <id>` header and a JSON array
of arguments. Action ids come from
`.next/server/server-reference-manifest.json`.

### 3.1 Authentication and login

#### A-1 — Two-factor is not enforced on server actions · High · Verified by running

> **Status, 12 November: Fixed in `6c7286f`.** Two-factor is enforced under every guard; only the three setup actions are exempt.

**Where.** `lib/merchant-action.ts:47-77` (`requireMerchantAction` never looks
at `twoFactorConfirmed`). The same gap in every action guarded only by
`requireRole("PLATFORM_ADMIN")`: `lib/actions/merchants.ts` (create, suspend,
set fee, **delete clinic**), `lib/actions/agency.ts`,
`lib/actions/impersonation.ts`, and `lib/actions/two-factor.ts`
(`resetTwoFactorByEmailAction`, `resetTwoFactorForUserAction`). The pages do
check: `lib/merchant-context.ts:53` and `:109`. Only
`lib/platform-admin-action.ts:36` checks on the action side.

**Reproduce.** With a platform admin that has a password but has never set up
two-factor:

1. Sign in at `POST /api/auth/callback/credentials` with `portal=admin`.
2. `GET /agency` → `307` to `/account/two-factor?required=1`. Correct.
3. `POST /m/<clinicId>/clients` with `Next-Action` for `clientAccountAction`
   and body `["<clinicId>","<customerProfileId>"]` →
   `{"ok":true,"account":{...}}`. The page was refused; the data was not.

**Impact.** "Two-factor is required for admins" is only true for people who
click. Anyone holding the password of an admin who has not enrolled — which
is every admin created with `REGISTRATION_SET_PASSWORD_DIRECTLY=1`, until
they enrol — can read and change any clinic, reset other admins' two-factor,
and delete clinics. They can also enrol their own authenticator and keep the
account.

**Fix.** Check `twoFactorConfirmed` in `requireMerchantAction` for the roles
in `TWO_FACTOR_REQUIRED_ROLES`, and replace every bare
`requireRole("PLATFORM_ADMIN")` in `lib/actions/` with
`requirePlatformAdminAction()`. Stronger: refuse to issue a staff session at
all to a required-role account without confirmed two-factor, and give it a
short-lived, setup-only session instead.

#### A-2 — The registration code is a master key · High · Read only

> **Status, 12 November: Mitigated in `f6c5908`.** A platform-wide limit of 20 wrong codes an hour now bounds guessing. The code still creates platform admins: unset `REGISTRATION_CODE` in production.

**Where.** `lib/actions/register.ts` (`registerPlatformAdminAction`, scope
`"ALL"`), `lib/registration-guard.ts:13-15` (10 attempts an hour per IP, 5 per
email address).

**Reproduce.** Open `/register/admin`, enter the code and your own email
address. With the flag off you receive a set-password link; with
`REGISTRATION_SET_PASSWORD_DIRECTLY=1` you choose a password on the form and
the account is active at once.

**Impact.** The code alone makes a platform admin with access to every
clinic. There is no approval step and no check that the registrant is
expected. The per-email limit does not slow guessing, because the attacker
picks the address; only the per-IP limit does, and addresses are cheap. See
S-1 for why the code may be weak.

**Fix.** Before go-live, unset `REGISTRATION_CODE` and
`REGISTRATION_SET_PASSWORD_DIRECTLY` in production — the pages then 404, and
admins invite admins from the console. If self-registration must stay, remove
the admin page from it, make the code long and random, and add a global
(not per-IP) attempt limit.

#### A-3 — Sign-in timing reveals which addresses have accounts · Medium · Verified by running

> **Status, 12 November: Fixed in `85681ed`.** Every refused sign-in does one password check's worth of work.

**Where.** `lib/auth-credentials.ts`: the unknown-address paths return before
`verifyPassword` (bcrypt, 12 rounds) at the `if (!(await verifyPassword(...)))`
line.

**Reproduce.** Four attempts each at `/api/auth/callback/credentials`,
`portal=admin`, wrong password: a known address took 0.28–0.34 s, an unknown
one 0.015–0.075 s.

**Impact.** The error text is deliberately identical, but the clock is not.
An attacker can list which addresses are admins, clinic staff, or clients of
a particular clinic.

**Fix.** When no account is found, run `verifyPassword` against a fixed dummy
hash before returning.

#### A-4 — Client sign-up says whether an address is already a client · Medium · Read only

> **Status, 12 November: Mitigated in `85681ed`.** Neutral message, and the real owner is emailed. A new address is still signed in on the spot and an existing one is not, so the outcomes differ. Closed only by A-6.

**Where.** `lib/actions/auth.ts`, `customerRegisterAction`:
`"An account with this email already exists."`

**Impact.** Anyone can ask a clinic's app whether a given person is a client
there. For a clinic, that is health-adjacent information.

**Fix.** Answer the same way in both cases ("check your email") and send the
existing client a "you already have an account" message instead.

#### A-5 — Anyone can lock an account out · Medium · Read only (counter behaviour observed)

> **Status, 12 November: Fixed in `6bffa29`.** Failures count against the address they came from (10 per 10 minutes), with a cap of 100 an hour on the account as a whole.

**Where.** `lib/login-limits.ts` (10 attempts per account per 10 minutes),
applied in `lib/auth-credentials.ts` before the password is checked. During
testing the counter for one account read 5 after one success and four
failures: every attempt counts, including the owner's own.

**Impact.** Ten requests every ten minutes keep a clinic owner or platform
admin locked out indefinitely, from anywhere, without knowing anything but
their email address.

**Fix.** Count failures only, and key the lock on account *and* source so a
stranger's failures do not block the owner; or slow attempts down
progressively instead of locking.

#### A-6 — Client accounts need no email verification · Medium · Read only

> **Status, 12 November: Open.**

**Where.** `lib/actions/auth.ts`, `customerRegisterAction` (account created
and signed in immediately; `emailConsent: true` set without being asked).

**Impact.** A stranger can create an account under someone else's address at
any clinic. The real owner gets a welcome email they did not ask for, cannot
register, and must use "forgot password" to take the account back — after
which they inherit whatever the stranger did. Email consent is recorded as
given when it was never asked.

**Fix.** Verify the address before the account can do anything, and record
email consent only from an explicit choice.

#### A-7 — A two-factor code can be used more than once · Low · Read only

> **Status, 12 November: Open.**

**Where.** `lib/totp.ts`, `verifyTotp`: accepts the previous, current and next
30-second step and keeps no record of the last step used.

**Impact.** Someone who sees a code being typed, and has the password, can
reuse that code for up to about 90 seconds.

**Fix.** Store the last accepted time step per user and refuse it and
anything older.

#### A-8 — Two-factor secrets are stored unencrypted · Low · Read only

> **Status, 12 November: Open.**

**Where.** `lib/two-factor.ts:14` reads `secret` straight from
`TwoFactorSecret`.

**Impact.** A database leak hands over every admin's second factor along with
their password hash. Backup codes, by contrast, are hashed.

**Fix.** Encrypt the secret with a key held outside the database.

#### A-9 — Password policy is minimal · Low · Read only

> **Status, 12 November: Open.**

**Where.** `lib/password-tokens.ts:13` (`MIN_PASSWORD_LENGTH = 8`, admins
included), `lib/actions/auth.ts` (clients: 8, no maximum), `lib/password.ts`
(bcrypt, 12 rounds — fine).

**Impact.** Eight characters with no check against known-breached passwords
is weak for accounts that hold client data. bcrypt also ignores everything
past 72 bytes, so two long passphrases sharing a prefix are the same
password.

**Fix.** Twelve characters for staff and admins (the registration form
already asks for this), a breached-password check, and a 72-byte cap or a
pre-hash.

#### A-10 — The rate limiter trusts `X-Forwarded-For` · Low on Vercel · Verified locally

> **Status, 12 November: Open.**

**Where.** `lib/request-ip.ts:7`, `lib/auth-credentials.ts` (`ipFromRequest`),
and the same line repeated in `lib/actions/password.ts` and
`lib/actions/clinic-directory.ts`.

**Reproduce.** Locally, each request with a different `X-Forwarded-For` value
got its own counter (`login:ip:10.9.9.1`, `login:ip:10.9.9.2`, …).

**Impact.** Wherever the header is client-controlled, every per-IP limit —
sign-in, registration code, password reset, uploads — is bypassed by changing
one header. **I did not verify this on Vercel**, which is documented to
overwrite the header; on Vercel today this is probably not exploitable. It
becomes exploitable the day the app sits behind anything else.

**Fix.** Read the address from one helper that prefers the platform's own
header (`x-vercel-forwarded-for`, then `x-real-ip`), and use it everywhere.

#### A-11 — Smaller points · Low / Info · Read only

> **Status, 12 November: Open.**

- `lib/actions/two-factor.ts`: `confirmTwoFactorSetupAction` and
  `disableTwoFactorAction` have no attempt limit (a signed-in session is
  needed first).
- `resetTwoFactorForUserAction` does not end the target's sessions, and
  nothing stops an admin resetting the only other admin.
- `lib/actions/impersonation.ts`: the `impersonate_session` cookie is set
  without `secure`; `stopImpersonationAction` closes whatever session id the
  cookie names.
- Password reset: the "account found" path sends an email and is slower than
  the "not found" path — the same timing signal as A-3, much weaker.

**Checked and found sound:** reset and invite links (256 random bits, stored
as SHA-256, single use by conditional update, 1 hour / 24 hours / 7 days,
bound to the account, sessions ended on use); the reset link's host comes
from configuration, never from the request, so it cannot be poisoned through
the `Host` header; sign-in is scoped by door, so the three account types on
one address do not interfere; sign-in logs contain reason codes and no email
addresses; the registration code is compared in constant time; redirects
after sign-in only go to same-origin paths the account may open.

### 3.2 Authorization and tenant isolation

#### T-1 — The Shop page shows other clinics' redemptions · High · Verified by running

> **Status, 12 November: Fixed in `6bd28ac`.** All six models are scoped, and a test fails for any model with a `tenantId` column that is not.

**Where.** `app/m/[merchantId]/shop/page.tsx:47`:
`ctx.db.redeemableItem.findMany({ where: { status: "REDEEMED" }, take: 25 })`.
`RedeemableItem` is missing from `TENANT_SCOPED_MODELS` in
`lib/tenant-db.ts:15-60`, so the scoped client does not add a clinic filter.

**Reproduce.** I created a second clinic with one redeemed item, then ran
exactly that query through `getTenantDb(<first clinic>)`. It returned the
second clinic's row: client name, item name and the staff note. The same
check on `CustomerProfile`, which is in the list, returned nothing.

**Impact.** Every clinic's staff see the 25 most recent collections across
the whole platform: other clinics' client names, what they came in for, the
free-text note, and the name and email of the staff member who handed it
over. With several clinics live this is a reportable personal-data breach on
day one.

**Fix.** Add `RedeemableItem` to `TENANT_SCOPED_MODELS`. Then make the list
impossible to forget: a test that reads `prisma/schema.prisma` and fails when
a model with a `tenantId` column is not in it. Today that test would flag
`RedeemableItem`, `PriceHistory`, `PackageSessionUse`,
`MembershipPriceChange`, `BirthdayGreeting` and `ClinicDomain`.

#### T-2 — The shop loads every clinic's price history and paid order lines · Medium · Read only

> **Status, 12 November: Fixed in `6bd28ac`.** Both queries name the clinic. The price-history half is tested; the order-lines half has no test of its own, because its effect never reached the output.

**Where.** `lib/client-app-catalog.ts:122` (`db.orderItem.findMany` filtered
only through `order: {...}`, which the scoped client does not touch) and
`:129` (`db.priceHistory.findMany` with no filter at all).

**Impact.** No other clinic's data reaches the screen — the results are
matched against this clinic's own ids — but every shop page load reads the
whole platform's rows. It gets slower with each clinic and is an easy way to
exhaust the database.

**Fix.** Add the clinic to both queries (`order: { tenantId }`, and `tenantId`
on price history).

#### T-3 — An unguarded function is exported as a server action · Low · Verified by running

> **Status, 12 November: Fixed in `b52de70`.** Both helpers deleted (neither was used), a third moved, and a test refuses any non-action export from an action file.

**Where.** `lib/actions/client-account.ts:252`,
`clientCreditBalance(customerProfileId)`: no session check, unscoped client.
Also `membershipDb` at `lib/actions/client-membership.ts:391`.

**What I found.** The function has an action id in the build manifest. It is
only bundled into the clinic's Clients page, so a staff session is needed to
reach it, and its id is not shipped to browsers. Calling it without a session
did not work. So: any signed-in staff member of any clinic who learned the id
could read any client's credit balance by profile id.

**Fix.** Move both helpers out of the `"use server"` files. Everything
exported from such a file is a public endpoint.

#### T-4 — Dead code with cross-clinic queries · Info · Verified (not reachable)

> **Status, 12 November: Fixed in `b52de70`.** Deleted, along with the unused actions in `appointments.ts`.

`lib/analytics.ts` has no importers; its `orderItem.groupBy` calls at lines
38, 45 and 108 would sum revenue across all clinics. `lib/actions/customers.ts`,
`loyalty.ts`, `locations.ts` and `settings.ts` are the old `/admin` actions;
they are not in the build manifest, so they cannot be called. Delete them —
`customers.ts:38` adjusts credit with a read-then-write that the current code
replaced with an atomic update, and it should not be found and reused.

**Checked and found sound:** all 132 exported actions were mapped to their
guard (the script is reproducible from the file list); apart from A-1 and
T-3, each one authenticates, and takes the clinic from the session or
verifies the named clinic against it. Clinic users naming another clinic get
the same refusal as a missing permission. Role and permission come from the
database on every request, not from the 30-day token. Raw SQL appears in
seven files and is parameterised in all of them.

### 3.3 Secrets and environment

#### S-1 — The example registration code is a six-digit number · High until confirmed otherwise · Read only

> **Status, 12 November: Fixed in the repository in `f6c5908`.** The example is empty and the runbook no longer shows a code. The same six-digit value remains in five test files as a fixture. **Still to do: check what production uses.**

**Where.** `.env.example:204` sets `REGISTRATION_CODE` to a concrete six-digit
value (not repeated here).

**Impact.** If production uses that value, everyone with repository access
has the master key from A-2. If production uses any six-digit number, there
are a million possibilities and the limit is ten guesses an hour per
address.

**Fix.** Check the production value today. Replace the example with an empty
value and a comment saying how to generate one (`openssl rand -base64 24`).

#### S-2 — `/api/internal/clinic-hosts` lists clinic domains · Info · Verified by running

> **Status, 12 November: Open.** By decision.

Unauthenticated by your decision. It returns every verified clinic domain
with its clinic slug — a customer list for anyone who asks. Both halves are
individually public, so this is a list, not a leak. A shared secret header
between middleware and the route would close it at no cost.

**Checked and found sound:** no real secret in tracked files or in any of the
181 commits (searched for Stripe live and restricted keys, webhook secrets,
Resend keys, AWS keys, private keys, database URLs with passwords). Key-shaped
strings in tests are 16–22 character dummies. No secret has a hard-coded
fallback. The only `NEXT_PUBLIC_` values are the build id and host names. No
client component reads a server variable. The cron route compares its secret
in constant time and refuses to run when the secret is unset.

**Not checkable from here — see the checklist in section 5(e):** how narrowly
the Vercel token, Stripe keys and R2 credentials are scoped, and whether they
have ever been rotated.

### 3.4 Payments and webhooks

#### P-1 — A negative quantity makes an order free · Critical · Verified by running

> **Status, 12 November: Fixed in `6ba3f68`.** Validated on the way in, re-checked at checkout, and enforced by database constraints.

**Where.** `lib/actions/client-app.ts:270`, `clientAddToCartAction`: `qty` is
typed as a number but never validated, and a TypeScript type is not a check
on what a browser sends. `clientSetCartQtyAction` at `:339` has the same gap.
The total is then floored at zero in `clientCheckoutAction`
(`Math.max(subtotal - ..., 0)`) and a zero total takes the "paid with credit"
path.

**Reproduce.** Signed in as a demo client:

1. `clientAddToCartAction("riverside-wellness","service",<€150 treatment>,1)`
2. `clientAddToCartAction("riverside-wellness","service",<€160 treatment>,-1)`
3. `clientCheckoutAction("riverside-wellness",null,{})` →
   `{"ok":true,"paid":true,"totalCents":0}`

The order was stored as `PAID` with subtotal −€10 and total €0, and **both**
treatments were issued to the client as collectable items — €310 of
treatments for nothing.

**Impact.** Any client of any clinic can take any product, treatment or
package without paying, as often as they like, and it appears in the clinic's
books as a completed sale.

**Fix.** Validate with zod in both actions: an integer from 1 to a sane
maximum. Re-check at checkout that every line has a positive quantity and a
positive total, and add a database `CHECK (quantity > 0)` on `BasketItem` and
`OrderItem`. Then search the action files for other arguments typed but not
parsed — this is a pattern, not a single slip (see R-2).

#### P-2 — Without a Stripe key, production marks every order paid · High · Read only

> **Status, 12 November: Fixed in `4797a8b`.** In real production a missing Stripe key blocks card payments, and the mock provider refuses.

**Where.** `lib/stripe-payments.ts:41`
(`if (!isStripeConfigured()) return { mode: "mock" }`) and
`lib/providers/payments/index.ts:7`, which returns the mock provider unless
`PAYMENT_PROVIDER` is exactly `"stripe"`.

**Impact.** A missing or mistyped environment variable — on a new project, a
rotated key, a preview promoted to production — and every checkout succeeds
without money moving. Nothing warns anyone. `MOCK_PAYMENTS_DECLINE` is read
in the same path.

**Fix.** When `isRealProduction()` is true, a missing Stripe configuration
must mean "blocked", and the mock provider must refuse to construct.

#### P-3 — Smaller points · Low · Read only

> **Status, 12 November: Open.**

- The cart keeps the price from when the item was added and does not re-check
  at checkout that the item is still active
  (`lib/actions/client-app.ts:475`). A client with an old cart pays an old
  price or buys an archived item.
- An order paid partly with credit and partly by card: refunding the card
  payment does not return the credit part (`lib/refunds.ts`, the Stripe
  branch).
- The manual backup code on a collectable item is 8 characters from a
  29-character alphabet. It is only accepted from signed-in staff of the same
  clinic, which is the real protection; `redeemItemAction` has no attempt
  limit.

**Checked and found sound:** webhook signatures are verified against both
secrets before anything is read; events are claimed in the database before
processing, so a replay or a concurrent duplicate does nothing, and a crashed
attempt is retried after five minutes; a payment is only completed when the
amount collected covers the amount due; an event from one connected account
cannot settle another account's payment. Refunds claim their amount in a
serializable transaction and are scoped to the clinic, so two staff cannot
refund the same money twice and one clinic cannot refund another's payment.
Credit and points are changed by a single conditional SQL update and cannot
go negative or be spent twice. Collectable-item tokens are 192 random bits
and redemption is a conditional update, so two scans cannot both succeed.
The check-in QR is signed, bound to the clinic, and expires in two minutes.

### 3.5 Input handling and injection

#### I-1 — The image endpoint fetches from any site · Medium · Verified by running

> **Status, 12 November: Fixed in `b9d8732`.** The optimiser accepts no remote host and no local path; nothing in the app uses it.

**Where.** `next.config.mjs`, `images.remotePatterns`:
`{ protocol: "https", hostname: "**" }`.

**Reproduce.** `GET /_next/image?url=https://www.wikipedia.org/portal/wikipedia.org/assets/img/Wikipedia-logo-v2.png&w=64&q=75`
→ `200 image/png`.

**Impact.** Anyone can use the deployment as an image proxy and resizer for
any site on the internet. On Vercel each new image is a billed optimisation.
It also makes the server fetch attacker-chosen URLs, and it is the endpoint
named in the critical Next.js advisory in D-1.

**Fix.** List only the hosts images really come from — the R2 public host and
nothing else.

#### I-2 — Push subscriptions accept any URL · Low · Read only

> **Status, 12 November: Open.**

**Where.** `app/api/push/route.ts`: `endpoint: z.string().url()`.

**Impact.** A signed-in client can register `https://anything` as their push
endpoint and press "send test"; the server then makes a request to it. The
response is not shown, but success and failure are, which is enough to probe
what the server can reach.

**Fix.** Require `https:` and a host on the short list of real push services
(Google, Apple, Mozilla, Microsoft).

**Checked and found sound:** the five uses of raw HTML in React are all built
on the server from fixed tables or a nonce; clinic-written text reaches the
client app, the portal and emails only through React's escaping or
`escapeHtml` (`lib/emails/layout.ts:24`), including names in subjects and
table rows; clinic-supplied links are validated as `https` URLs; `next`
parameters are restricted to same-origin paths and then to paths the account
may open; server actions are protected against cross-site requests by Next's
origin check and all session cookies are `HttpOnly` with `SameSite=Lax`; no
CORS headers are set anywhere.

**Not checked:** the text-check feature and ways round it; prototype
pollution; whether every `FormData` field in the App Builder forms is
allow-listed (I sampled the settings and catalogue actions, which are).

### 3.6 File uploads and storage

No findings above Info.

**Checked and found sound** (`app/api/uploads/route.ts`,
`lib/providers/storage.ts`, `lib/image-pipeline.ts`): only clinic staff can
upload; the type is decided from the file's first bytes, not its name or
declared type; SVG and HTML are not accepted; every image is decoded and
re-encoded, with a pixel limit, before it is stored; the stored name is
random and the original filename is discarded; 15 MB and 30 uploads a minute.

**Info.** Objects are public and never deleted, so a replaced logo or product
photo stays reachable by its old address forever. All clinics share one
folder. The request body is parsed before the session is checked.

**Not checkable from here:** whether the bucket allows listing, and its CORS
and lifecycle rules — see section 5(e).

### 3.7 Hosts, domains and white label

#### H-1 — A removed clinic domain can be claimed by someone else · Medium · Read only

> **Status, 12 November: Open.**

**Where.** Operational, around `lib/actions/clinic-domains.ts`
(`removeClinicDomainAction`).

**Impact.** When a clinic's domain is removed here but its DNS record still
points at Vercel, any other Vercel customer can add that name to their own
project and serve whatever they like on the clinic's address — to clients who
have it on their home screen.

**Fix.** On removal, tell the admin in the console that the DNS record must
be deleted, and have the hourly re-check flag domains whose record still
points here after removal. Add the step to
`docs/operations/clinic-domains.md`.

#### H-2 — Host headers are trusted because Vercel sets them · Info · Verified locally

> **Status, 12 November: Open.** Informational.

`middleware.ts`, `lib/request-origin.ts`, `app/api/push/route.ts` and others
read `x-forwarded-host` before `host`. That is correct behind Vercel and
unsafe behind anything that passes the header through. I tested whether a
forged `Host` could make middleware fetch its clinic-host map from an
attacker's server: it could not (no request arrived at a listener I set up).

**Checked and found sound:** only platform admins can attach a domain, and
the platform's own names, hosting-provider names, IP addresses, local names
and bare apex domains are refused; a clinic's domain cannot open the portal,
the admin console, sign-in or registration; legacy `pirs.io` redirects go
only to a fixed list of hosts, so they cannot be turned into an open
redirect; the `x-clinic-host` header is stripped from incoming requests
before middleware sets its own.

**Not checked:** that the apex and `www` are really not served (a DNS and
Vercel-project question); cache behaviour at Vercel's edge.

### 3.8 Push, email and notifications

#### N-1 — Clinic broadcasts ignore consent and quiet hours · Medium · Read only

> **Status, 12 November: Fixed in `e69580a`.** Broadcasts go through the same consent, sending-hours and daily-limit checks as campaigns.

**Where.** `lib/actions/clinic-broadcast.ts` calls `sendToClinicClients`
(`lib/web-push.ts`), which sends to every push subscription of the clinic.
The campaign path goes through `sendMarketingTo` (`lib/marketing.ts:126`,
`:133`), which checks both. The broadcast path does not.

**Impact.** A client who switched offers off still receives every broadcast,
at any hour. The limit is five an hour per clinic.

**Fix.** Send broadcasts through `sendMarketingTo`, or define them as
service messages and restrict what they may say.

#### N-2 — Turning on notifications also turns on marketing · Medium · Read only

> **Status, 12 November: Fixed in `e69580a`.** Offers are asked for with their own unticked box; only a tick is recorded.

**Where.** `app/api/push/route.ts`: on first subscribe, `marketingConsent` is
set to true with source `"push-opt-in"`.

**Impact.** Agreeing to order updates is recorded as agreeing to offers.
Under the GDPR, consent to marketing has to be asked separately.

**Fix.** Leave marketing consent as it was and ask on its own.

#### N-3 — A closed account still receives broadcasts · Low · Read only

> **Status, 12 November: Fixed in `e69580a`.** Closing an account deletes its push subscriptions.

**Where.** `lib/actions/client-app.ts`, `clientDeleteAccountAction`: the
account is disabled and consents cleared, but push subscriptions are kept,
and N-1 means broadcasts do not look at consent.

**Fix.** Delete the client's push subscriptions when the account is closed.

**Checked and found sound:** who can send — `messages.send` permission,
clinic taken from the verified session, recipients selected by clinic id;
emails are sent through the provider's API with escaped content, so there is
no header injection; links in emails are built from configuration and the
clinic's verified domain, not from the request.

### 3.9 Security headers and client side

#### C-1 — Missing headers · Low · Verified by running

> **Status, 12 November: Partly fixed in `5c49bbd`.** `Permissions-Policy` added and `X-Powered-By` removed. The breadth of `style-src` and `img-src` is unchanged.

Observed on the local build's `/login`: a strict nonce-based content security
policy, `X-Frame-Options: DENY`, `nosniff`, a sensible referrer policy, and
`Cache-Control: private, no-store` on pages. Missing or improvable:

- No `Permissions-Policy` (camera is needed for the QR scanner; everything
  else can be denied).
- `X-Powered-By: Next.js` is sent (`poweredByHeader: false`).
- `style-src 'unsafe-inline'` and `img-src https:` are broader than needed.

**Checked and found sound:** the service worker caches only static files and
never pages or API responses; browser storage holds a list of recently viewed
items and a few display flags, no tokens and no personal data; no source maps
are shipped.

**Not verified:** HSTS and the `__Secure-` cookie names only appear over
HTTPS, and staging is behind Vercel's login wall (see section 4), so I could
not observe them on a real deployment.

### 3.11 Data protection and logging

#### L-1 — "Delete my account" does not delete · Medium · Read only

> **Status, 12 November: Open.**

**Where.** `lib/actions/client-app.ts`, `clientDeleteAccountAction`: the
account is disabled; the profile, history and notes remain.

**Impact.** That may be right for financial records, and the code says so —
but there is no process to erase the rest, no export of a client's data, and
no retention period after which anything is removed.

**Fix.** Decide and document what is kept, why, and for how long; add an
erasure step for everything else, and an export.

#### L-2 — Smaller points · Low · Read only

> **Status, 12 November: Partly fixed in `5c49bbd`.** The email address is out of the log lines. The other two points are open.

- `lib/client-notifications.ts:150` logs the recipient's email address on a
  failed send.
- Error reports to Sentry and the error webhook carry the full error message
  and stack (`lib/observability.ts`). Database errors can include field
  values. The request path is sent without its query string, so tokens in
  links are not leaked this way.
- Two-factor secrets in clear text (A-8) and health-adjacent free text
  (redemption notes, client notes) sit in the same database with no
  field-level protection.

**Not checked:** where each provider stores data (Neon region, R2 location,
Resend, Stripe, Vercel log retention), and whether processing agreements are
in place. Vercel's response id showed `fra1` (Frankfurt) for staging, which
says where that request was served and nothing more.

### 3.13 Resilience and abuse

#### R-1 — Cost abuse · Medium · Read only (I-1 verified)

> **Status, 12 November: Partly fixed.** The two cost routes named here are closed by I-1 and T-2. Sign-up email volume is unchanged (A-6).

The open image endpoint (I-1) and the unbounded shop queries (T-2) are the
two ways a stranger can run up a Vercel or Neon bill. Client sign-up sends a
welcome email to any address, 5 per address and 20 per IP in 15 minutes
(A-6, A-10).

#### R-2 — Action arguments are typed, not validated · Medium · Read only (P-1 verified)

> **Status, 12 November: Fixed in `04ca805`.** Every client-side action checks every argument, and a test fails for any that does not. See the addendum below.

P-1 is one instance of a wider habit in `lib/actions/client-app.ts` and
`lib/actions/appointments.ts`: arguments such as `qty`, `durationMinutes`,
`dateIso`, ids and option objects are declared with TypeScript types and
used directly. Anything a browser can send will arrive. The clinic-side
actions mostly parse with zod; the client-side ones mostly do not.

**Fix.** Every exported action parses every argument with zod before use. A
lint rule or a wrapper makes this checkable.

#### R-2 addendum — Found while fixing: a client could write to any column of their own profile · High · Verified by test

> **Status, 12 November: Fixed in `04ca805`.**

**Where.** `lib/actions/client-app.ts`, `clientSaveConsentAction`: the
`consent` argument was spread straight into an update of the client's own
profile row (`data: { ...consent, ... }`).

**Impact.** A request carrying `accountCreditBalanceCents` or
`loyaltyPointsBalance` next to the four switches set those too. A client
could give themselves account credit or points — the same end result as P-1,
by a different route. I did not find this in the review; it surfaced when
every argument was given a schema.

**Fix.** The schema is strict (four booleans, nothing else) and the update
names its four fields instead of spreading anything. The attack is kept as a
test in `tests/integration/client-action-args.test.ts`.

## 4. What I did not check

- **Production.** Nothing about the live deployment, its environment
  variables or its database.
- **Staging, beyond its front door.** Every path on `staging.deza.ai`
  redirects to Vercel's own sign-in (deployment protection). That keeps the
  demo index and seeded accounts private, which is good, but it means no
  application header, cookie or page on staging was observed. It also means
  Stripe webhooks and cron calls to staging are blocked unless bypass is
  configured — worth confirming.
- **The dashboards** of Vercel, Neon, Stripe, Cloudflare R2, Resend and
  GoDaddy. Section 5(e) is the list.
- **Real devices.** No iPhone or Android phone; nothing about installed-app
  behaviour.
- **The portal screens in a browser.** Clinic and admin sign-in need
  two-factor; I tested the actions behind them directly instead.
- **Exhaustive reading.** I mapped all 132 actions to their guards and read
  the authentication, payment, refund, webhook, upload, push, domain and
  settings code in full. I did not read every line of the App Builder,
  booking, membership-billing and cron code; a flaw of the P-1 kind could be
  there.
- **Specific items:** the text-check feature; prototype pollution; test
  quality; `X-Forwarded-For` behaviour on Vercel; HSTS and secure cookie
  names over HTTPS; whether `npm audit` advisories are exploitable here;
  load and denial-of-service testing; email deliverability and spoofing
  (SPF, DKIM, DMARC).
